# 保存・履歴表示の性能検証

## 再実行

```bash
pnpm benchmark:storage
```

2 MB以内の合成イベントを使い、`parseState` と `saveToStorage` をそれぞれ10回ウォームアップした後、15回の中央値を出力します。保存先はメモリ上のMapで、ブラウザや実際の利用者のデータにはアクセスしません。

`saveToStorage` の計測には、シリアライズ、保存するデータと前回データの検証、競合確認、バックアップと主データの書き込みを含みます。ブラウザのディスクI/O、Reactの描画、Provider側の容量確認は含みません。実機の入力応答時間を示す数値ではありません。

## 2026-09-13の比較

Apple M3 Pro / Node.js v25.2.1。変更前は `bfc6ab0`、変更後はID重複判定・対象者検索をSetに変更した実装。同じスクリプト・データで比較しました。

| 人数 | 支払い件数 | JSONバイト数 | 読み取り：変更前 → 後 | 保存：変更前 → 後 |
| ---: | ---------: | -----------: | --------------------: | ----------------: |
|    2 |      1,000 |      226,272 |        5.66 → 1.38 ms |   10.38 → 3.22 ms |
|    2 |      3,000 |      680,272 |       13.92 → 3.73 ms |  31.18 → 10.09 ms |
|    2 |      6,000 |    1,361,272 |       50.64 → 7.80 ms | 107.54 → 19.22 ms |
|  100 |      1,000 |    1,891,624 |      19.43 → 13.26 ms |  43.89 → 31.73 ms |

支払いIDの重複判定は、それまで読み取った全レコードの走査からSetへの照会に変更しました。対象者の並べ替えもSetを利用し、メンバー登録順と端数配分を維持しています。検証の省略、保存の遅延化、保存形式の変更は行っていません。

単体テストでは上限10,000件の読み取り、末尾の重複ID・不正な対象者、件数超過、6,000件の同期保存とバックアップ保持、100人での対象者順と端数配分を検証します。時間は実行環境・JIT・GCで変動するため、CIに時間の合否基準は設けていません。

ブラウザテストでは、6,000件のイベント名を1文字ずつ入力し、直後の再読み込みでイベント名と全支払いが保持されることをChromium（PC・320px幅）とWebKit（390px幅）で確認します。

## 履歴の描画上限

支払い画面と精算画面で共用する履歴を、全件描画から20件単位のページ表示へ変更しました。内容・支払者名・対象者名の検索は全件を対象に行い、表示中の記録だけを編集・削除できます。検索用データとメンバー名の索引は、支払い・メンバーの変更時に再作成します。履歴の絞り込みは保存データ・合計・精算・共有テキストに渡しません。

ローカルの本番ビルド、Chromium、320×800の表示領域、2人・1,000件の合成イベントで比較した結果です。変更前は `505dc83` と同じファイル内容です。

| 支払い履歴                | 変更前 | 変更後 |
| ------------------------- | -----: | -----: |
| 描画する記録数            |  1,000 |     20 |
| 履歴リスト内部のDOM要素数 | 33,000 |    660 |

DOM要素数は98%減少しました。画面全体の速度が98%向上したという意味ではありません。タイミングによる不安定な合否判定を避け、ブラウザテストでは両画面の描画が20件以内に収まることと、先頭ページにない記録の検索・編集、末尾削除後のページ調整、入力途中の支払いの保持、全件での精算・一括コピーを検証します。
